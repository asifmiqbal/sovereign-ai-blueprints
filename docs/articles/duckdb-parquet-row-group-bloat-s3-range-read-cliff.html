Parquet Row-Group Bloat: Why AI Agents Pull 500MB for a 4KB Lookup

Unsorted 512MB Parquet row groups force 492MB S3 downloads for 4KB lookups. Clustering 64MB row groups with PageIndex and Bloom filters cuts transfers by 99.96%.

Apache Parquet files written with default 512MB unsorted row groups force analytical AI agents using DuckDB, Polars, or Trino to download 492MB from S3 or Wasabi just to retrieve a single 4KB customer record. Sorting writes by (tenant_id, event_ts), sizing row groups to 64MB, and enabling Parquet v2 PageIndex headers with split-block Bloom filters reduces S3 byte-range transfers to 184KB (-99.96% bandwidth) and cuts P95 query latency from 3,840ms to 68ms.

Modern AI data architectures frequently bypass traditional data warehouses by equipping autonomous agents with embedded SQL engines (DuckDB, DataFusion, Polars) that query Apache Parquet tables directly over S3-compatible object storage. When an enterprise remedies the [small-file Iceberg lakehouse explosion](/articles/small-file-lakehouse-explosion-iceberg-compaction) by compacting thousands of tiny JSON logs into 1GB Parquet files, batch scan throughput improves immediately.

Then an AI copilot starts running high-concurrency point lookups (WHERE tenant_id = 'T-849' AND order_id = 'ORD-9921') against those compacted 1GB Parquet files. Suddenly, network interfaces saturate at 10 Gbps, DuckDB worker containers crash with Out-Of-Memory (OOM) errors, and query latency spikes past three seconds. You can't use HTTP Range requests to surgically fetch a 4KB row if your Parquet writer never wrote page-level offset indexes or sorted the data before compression.
