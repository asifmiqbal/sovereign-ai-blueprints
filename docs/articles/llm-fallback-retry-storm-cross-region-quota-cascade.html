LLM Fallback Retry Storms: Stopping 4x Token Spend Spikes

Nested SDK and AI gateway retries multiply 32K-token prompts by 9x during HTTP 429 rate limits. Single-owner retry budgets and prefill guards cap overhead at 1.04x.

LiteLLM and Envoy AI gateways paired with default application SDK settings (max_retries=3) trigger 9x multiplicative request amplification whenever a primary cloud LLM region hits an HTTP 429 or drops a streaming SSE socket mid-generation. Enforcing max_retries=0 at the client SDK, capping gateway retry budgets at 20%, and blocking automatic retries after prompt prefill completion eliminates cross-region quota cascades and caps failover overhead at 1.04x.

Every production AI engineering team configures multi-region or multi-provider fallbacks (us-east-1 $\rightarrow$ eu-west-1 $\rightarrow$ ap-southeast-1, or Claude Sonnet $\rightarrow$ GPT-4o $\rightarrow$ Gemini Pro) to protect uptime against regional rate limits (HTTP 429) and provider overload (HTTP 529). On paper, routing around a degraded region should cost exactly the same number of tokens as a normal request.

In production, naive fallback chains routinely multiply your hourly token bill by 4.1x while knocking over every backup region in under ninety seconds. Why? Because application developers and platform engineers don't disable the default retry loops inside each layer of the stack, and traditional HTTP proxies can't see how Server-Sent Events (text/event-stream) bill prompt prefill tokens before a streaming timeout occurs. You won't survive a regional brownout if every dropped socket re-bills a 32,000-token prompt four times.
